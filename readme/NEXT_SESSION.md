# Правила работы с AI-ассистентом

## Режим: Консультации

- Перед тем как подготавливать и предоставлять блоки кода обсуждаются архитектурные и 
  другие вопросы, до согласования выбранного решения код для внесения в проект не 
  предоставляется.
- Все технические решения должны по максимому соответствовать промышленным стандартам, уровень advanced
должен рассматриваться как базовый. Менее значимый применяется в том случае ели advanced применять не эффективно.
- Выдаёт готовые блоки кода с комментариями
- Пользователь вносит САМ изменения в проект
- Указывает файл, номера строк и что именно изменить (вставить / заменить / удалить)
- **Не** редактирует файлы проекта самостоятельно
- **Не** запускает команды сборки и прошивки
- На постоянной основе корректирует план и отчет: после обсуждения и согласования до корректировки (или во время) проекта.
- В базовом режиме работает как учитель-консультант: помогает изучать архитектуру, объясняет решения, подготавливает инструкции и готовые блоки кода, а пользователь самостоятельно вносит изменения в проект.
- По отдельной явной просьбе пользователя может добавить или изменить код в проекте; это является исключением из базового режима самостоятельного редактирования пользователем.
- Каждый предлагаемый блок кода обосновывать конкретным применением в текущем согласованном вертикальном срезе: какую задачу он решает, где вызывается или используется и почему необходим.
- Не добавлять неиспользуемые функции, интерфейсы, параметры, зависимости и абстракции «на будущее». Реализовывать функциональность только при возникновении конкретной потребности в текущем срезе.
- Перед предоставлением кода проверять необходимость каждого элемента. Если он дублирует уже имеющийся механизм или не имеет конкретного применения, исключать его из предложения. Требование уровня advanced не является основанием для избыточного функционала.

## Объяснение кода и изучение C++

- Пользователь работает на C; практики с C++ пока немного. Объяснять C++ с опорой на знакомые конструкции C, отмечая сходства и отличия.
- Разбирать код небольшими последовательными блоками. Переходить к следующему блоку после сигнала пользователя, отвечая на вопросы по текущему блоку до продолжения.
- Новые конструкции C++ (пространства имён, `std::`, ссылки, преобразования типов и другие) объяснять по мере появления в коде проекта, простыми словами и с короткими примерами.
- Не предполагать, что пользователь уже знаком с терминологией C++. При необходимости различать этапы препроцессирования, компиляции и выполнения программы.
- Сохранять этот формат в следующих сессиях без повторного согласования.
- После теоретических обсуждений пополнять [CPP_NOTES.md](CPP_NOTES.md) кратким резюме разобранных вопросов C++ с опорой на опыт C и примеры проекта. Пользователь поручил вести этот конспект; его обновление не означает разрешения самостоятельно изменять код проекта.

## Точка остановки — 2026-09-08

Продолжаем вертикальный срез `TEST_PING`: эмулятор → UART → парсер → q_input → Command_Task → диагностика. Затем расширяем путь командой `AUDIO_POWER` до ИК-передачи.

### Что готово

- PlatformIO: `esp32dev`, Arduino, `src_dir = APP`; точка входа `APP/Main/src/main.cpp`.
- Эмулятор `tools/vc02_emulator/vc02_emulator.py` реализован и разобран. В `tools/.venv` установлен `pyserial 3.5`. Пользователь подтвердил `0x01 --dry-run`: `5A 01 00 00 5B`.
- Командный кадр: `5A commandId 00 00 XOR`. Номер `TEST_PING` ещё не назначен; `0x01` пока только пример. Параметры настоящего VC-02 предстоит подтвердить.
- Выбран встроенный USB–UART-мост платы и `Serial`, 115200 8N1. Отдельного адаптера у пользователя нет.
- `Uart_Drv`: `Init()` и `ReadByte(std::uint8_t&)`. Неиспользуемая `Available()` удалена. Ссылку как выходной параметр оставили по решению пользователя.
- `Vc02_Protocol_Srv`: сборка пяти байт, резервные нули, XOR, восстановление по следующему старту. Тайм-аут 100 мс проверяется при следующем байте по времени обработки, а не физического поступления в UART.
- Типы `InputCommand`, `DeviceCommand`, `IrJob`, `DiagnosticEvent` готовы. Перечисления DeviceCommand и DiagnosticEvent вложены в структуры. Структуры заполняем присваиваниями по именам полей после `{}`.
- По явной просьбе пользователя реализовано создание сразу всех пяти очередей. `App_Config::Queues`: INPUT/AUDIO/TV/IR_TX — по 8 элементов, DIAG — 32.
- `App_Context::CreateQueues()` создаёт очереди, проверяет общий результат, при частичной ошибке удаляет созданные очереди и сбрасывает дескрипторы. Вызывать один раз до запуска задач с исходными nullptr.
- `Uart_Task::Run()` реализована и разобрана: порции до 64 байт, пауза один тик, парсер, назначение requestId с пропуском нуля, передача InputCommand и диагностических событий.
- В q_input — одна отправка с ожиданием до 30 мс; при тайм-ауте команда отклоняется с INPUT_QUEUE_FULL. В q_diag — без ожидания, при заполнении событие отбрасывается.
- Из Uart_Task удалены повторные configASSERT по решению пользователя. Корректность контекста и создание очередей обеспечиваем при запуске.
- Ветка Accepted пока выражена через else после исключения Waiting и Rejected; добавлены поясняющие комментарии. Изменение логики не согласовано.

### С чего начать следующую сессию

1. Сначала прочитать правила выше и эту точку остановки.
2. Согласовать номер TEST_PING и минимальное поведение Command_Task: получение InputCommand из q_input, TEST_PING_HANDLED для известной команды, COMMAND_REJECTED для неизвестной, сохранение requestId в диагностике.
3. Дать код небольшими блоками; пользователь вносит, агент проверяет. Затем реализовать Diagnostic_Task.
4. Согласовать и подключить запуск: постоянное время жизни контекста, Init UART, CreateQueues и проверка результата, создание задач и обработка ошибок запуска.
5. Пользователь выполняет сборку и аппаратный тест. После прохождения TEST_PING перейти к AUDIO_POWER.

Перед разрешённым редактированием агентом пользователь должен сохранить текущий файл в VS Code: уже возникал конфликт несохранённой вкладки с изменённым файлом на диске. Без необходимости не переписывать пользовательский код.
