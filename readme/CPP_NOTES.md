# C++: резюме обсуждений

Конспект для разработчика с опытом C. Здесь фиксируем разобранные вопросы на примерах Voice Controller. Новые темы добавляем после обсуждения, небольшими разделами: смысл, пример, отличие от C и важные ограничения.

## 1. Заголовки, препроцессор и выполнение программы

Заголовочный файл `.h` обычно не компилируется отдельно. Директива `#include` условно вставляет его содержимое в место подключения. После препроцессирования компилятор обрабатывает получившуюся единицу трансляции: исходный `.cpp` вместе с подключёнными заголовками. Затем компоновщик связывает результаты компиляции в программу.

Это происходит на компьютере до загрузки прошивки. `setup()` и `loop()` выполняются на ESP32 уже после сборки и загрузки; обработка `#include` не является частью их выполнения.

В заголовках обычно размещают объявления интерфейса, а в `.cpp` — определения обычных функций. Заголовок сообщает вызывающему коду, как обратиться к функции; тело функции компилируется в составе её `.cpp`.

## 2. Защита от повторного подключения

```cpp
#pragma once
```

Предотвращает повторную обработку одного заголовка в пределах одной единицы трансляции. Например, `Uart_Task.cpp` подключает `Uart_Drv.h` напрямую и через другой заголовок — содержимое `Uart_Drv.h` обрабатывается один раз.

Другой `.cpp` обрабатывается независимо и тоже может подключать этот заголовок. Это не ограничение «один раз на весь проект».

`#pragma once` поддерживается распространёнными компиляторами как в C, так и в C++, но не входит в стандарты этих языков. Стандартный вариант для обоих языков — include guard:

```c
#ifndef VOICE_CONTROLLER_UART_DRV_H
#define VOICE_CONTROLLER_UART_DRV_H

/* Объявления интерфейса. */

#endif
```

IDE может добавить защиту по шаблону. Само расширение `.h` защиту не создаёт.

## 3. Стандартные целочисленные типы

```cpp
#include <cstddef>
#include <cstdint>
```

- `<cstddef>` предоставляет `std::size_t`: беззнаковый тип для размеров и количества элементов. Его разрядность зависит от платформы.
- `<cstdint>` предоставляет целочисленные типы, включая доступные на нашей ESP32 `std::uint8_t` и `std::uint32_t`.
- `std::uint8_t` — ровно 8 бит, диапазон 0–255.
- `std::uint32_t` — ровно 32 бита, диапазон 0–4 294 967 295.

Типы с точной разрядностью стандарт предоставляет при наличии подходящих типов на платформе. В C соответствующие заголовки — `<stddef.h>` и `<stdint.h>`, а имена используются без `std::`.

## 4. Пространства имён и `std::`

Пространство имён объединяет имена и помогает избежать конфликтов. Оно не является типом данных или объектом.

```cpp
namespace Uart_Drv {
    void Init();
}

namespace Ir_Drv {
    void Init();
}
```

Вызовы различаются полными именами:

```cpp
Uart_Drv::Init();
Ir_Drv::Init();
```

В этих выражениях `::` уточняет, в каком пространстве искать имя справа. В C для похожей организации обычно используют префиксы: `Uart_Drv_Init()` и `Ir_Drv_Init()`.

`std` — пространство имён стандартной библиотеки C++. Оно позволяет стандартным именам, например `count`, сосуществовать с пользовательскими именами.

```cpp
std::uint8_t value;
```

Здесь `std::` относится к имени типа `uint8_t`; `value` — наша переменная. Префикс не распространяется на последующий код и не означает обязательный вызов функции: он может уточнять и имя типа.

Если написать `uint8_t` без `std::`, компилятор ищет неуточнённое имя по правилам поиска имён. Если оно недоступно, возникает ошибка. Некоторые заголовки также предоставляют `uint8_t` в глобальном пространстве, но полагаться на это при использовании `<cstdint>` не следует. Конкретное имя можно явно сделать доступным:

```cpp
using std::uint8_t;
uint8_t value;
```

В текущем драйвере используем полные имена `std::uint8_t` и `std::uint32_t`. Обсуждение `std::size_t` сохранено в разделе 9.

### Вложенные пространства имён

Пространства имён можно вкладывать друг в друга. В конфигурации проекта выделяем настройки очередей в группу `Queues`:

```cpp
namespace App_Config {
    namespace Queues {
        constexpr std::uint32_t INPUT_LENGTH = 8;
    }
}
```

Полное имя константы — `App_Config::Queues::INPUT_LENGTH`: в `App_Config` находим `Queues`, затем в нём `INPUT_LENGTH`. Так настройки разных частей приложения можно группировать по назначению, сохраняя общий раздел конфигурации.

Вложенность организует имена и не создаёт объектов или дополнительных действий при выполнении программы. Это не механизм ограничения доступа: именованные пространства имён не делают свои объявления закрытыми.

## 5. Функции пространства имён и методы объекта

```cpp
Uart_Drv::Init();  // Обычная функция в пространстве имён.
Serial.begin(115200, SERIAL_8N1);  // Метод существующего объекта Arduino.
```

`Uart_Drv` объединяет наши функции, а они вызывают методы объекта `Serial`. Пространство имён не «хранит методы другого объекта».

Методом обычно называют функцию-член класса или структуры C++. Например:

```cpp
struct Uart {
    void Init();  // Объявление метода; определение здесь не показано.
};

// Внутри вызывающей функции:
// Uart uart;
// uart.Init();
```

В отличие от пространства имён, `Uart` здесь является типом, экземпляр которого можно создать. Детали классов и методов разберём отдельно по мере необходимости.

## 6. Состояние и выбор между функциями и классом

Состояние — данные, сохраняемые между вызовами: настройки порта, состояние его открытия, содержимое приёмного буфера.

В текущем `Uart_Drv` нет собственных данных, сохраняемых между вызовами. Локальные переменные `count` и `received` используются только во время вызова соответствующей функции. Состоянием UART управляют `Serial` и нижележащая реализация драйвера.

`Init()` вызываем один раз при запуске, а функции чтения — многократно. Однократность инициализации сама по себе не означает отсутствия состояния.

Для текущего интерфейса достаточно функций в пространстве имён. Класс может понадобиться для нескольких независимо настроенных UART, но полезен и для единственного объекта, если нужно объединить данные с операциями, защищать согласованность состояния или управлять временем жизни ресурса.

Пространство имён само по себе не запрещает переменные — мы просто не объявляли в нём собственное сохраняемое состояние.

## 7. Глобальное пространство имён и связывание

Это разные характеристики:

- Пространство имён определяет, где объявлено имя и как его найти, например `Uart_Drv::Init`.
- Связывание определяет, могут ли объявления в разных единицах трансляции обозначать одну функцию или переменную.

Примеры для обычных функций вне классов:

| Объявление | Где находится имя | Связывание |
|---|---|---|
| `void Init();` | Глобальное пространство | Внешнее |
| `static void Init();` | Глобальное пространство | Внутреннее |
| `namespace Uart_Drv { void Init(); }` | `Uart_Drv` | Внешнее |
| `namespace Uart_Drv { static void Init(); }` | `Uart_Drv` | Внутреннее |

`static` у такой функции работает и в C, и в C++: функцию с внутренним связыванием нельзя вызвать из другого `.cpp` по внешнему объявлению её имени. В другом `.cpp` может существовать независимая `static`-функция с тем же именем.

Для вызова обычной функции с внешним связыванием из другого `.cpp` вызывающая сторона должна видеть подходящее объявление, обычно из заголовка, а определение должно участвовать в компоновке.

Таким образом, **глобальное пространство имён не означает доступность всем файлам**. Функция может иметь имя в глобальном пространстве и внутреннее связывание. И наоборот, функция в `Uart_Drv` может иметь внешнее связывание и вызываться из других `.cpp`.

`#pragma once` решает другую задачу: защищает заголовок от повторной обработки, но не управляет связыванием функций.

## 8. Аргумент по умолчанию

```cpp
namespace Uart_Drv {
    void Init(std::uint32_t baudRate = 115200);
}
```

В C++ можно вызвать эту функцию двумя способами:

```cpp
Uart_Drv::Init();      // Компилятор использует аргумент 115200.
Uart_Drv::Init(9600);  // Используется явно переданный аргумент.
```

В C у обычных функций такого механизма нет. В нашем проекте значение по умолчанию указываем в объявлении заголовка, доступном вызывающему коду, и не повторяем его в определении `.cpp`.

## 9. Преобразование `int` в `std::size_t`

Учебный пример из обсуждения: функция `Available()` впоследствии удалена из драйвера как неиспользуемая. Ниже сохранено объяснение типов, а не описание текущего интерфейса.

`Serial.available()` возвращает `int`, а наша `Uart_Drv::Available()` возвращает `std::size_t`, подчёркивая, что результат — количество байт. Поэтому после проверки положительности используется `static_cast<std::size_t>(count)`. Это явное преобразование типа, а не перевод числа в байты. Для допустимого положительного значения само число сохраняется.

Запись `return count;` тоже преобразовала бы результат в тип, объявленный у нашей функции, но неявно. Присваивание результата `Serial.available()` сразу в `unsigned int` или `std::size_t` также не устраняет преобразование: исходный тип метода остаётся `int`. Отрицательное значение при переводе в беззнаковый тип становится большим положительным числом.

На используемой ESP32 `int` и `std::size_t` имеют размер 32 бита, но первый тип знаковый, второй — беззнаковый. На других платформах их размеры могут различаться. Возвращать из обёртки `int` тоже корректно; `std::size_t` здесь выбран для выражения смысла интерфейса.

## 10. Анонимное пространство имён

`namespace { ... }` без имени используют в `.cpp` для внутренних данных и функций. Они имеют внутреннее связывание: другой `.cpp` не может обратиться к ним через внешнее объявление `extern`.

```cpp
namespace Vc02_Protocol_Srv {
    namespace {
        std::uint8_t receivedCount = 0;
    }

    // В функциях парсера в этом же пространстве и файле
    // можно обращаться по обычному имени: receivedCount = 0;
}
```

Внешнее именованное пространство `Vc02_Protocol_Srv` группирует имена, но само по себе не скрывает данные от других `.cpp`. Внутреннее анонимное пространство ограничивает связывание. Для переменной это похоже на файловое `static` в C; файловый `static` также работает в C++.

В нашем парсере так размещены буфер, счётчик байтов, время последнего байта и константа тайм-аута. Задача взаимодействует с ними через `ProcessByte()`, а не изменяет счётчик напрямую. Это организация доступа при сборке программы, а не защита памяти во время выполнения. Данные сохраняются между вызовами функций.

## 11. FreeRTOS и C++

В эту главу добавляем разобранные элементы FreeRTOS по мере их применения в проекте. FreeRTOS предоставляет C API, которое мы вызываем из C++: очереди и задачи не становятся классами C++ автоматически.

### 11.1. Очереди

Очередь позволяет одной задаче передать данные другой. В нашем проекте, например, `Uart_Task` передаёт проверенную `InputCommand` через `q_input` в `Command_Task`.

Очередь как структура данных не зависит от FreeRTOS: её можно реализовать, например, кольцевым буфером на C и использовать без операционной системы. В проекте выбрана реализация FreeRTOS, потому что она дополнительно обеспечивает безопасное одновременное обращение задач, блокирующее ожидание данных или свободного места, пробуждение ожидающих задач и тайм-ауты ожидания. Эти возможности связаны с планировщиком RTOS. Сама очередь не защищает произвольные данные вне неё — например, объекты, указатели на которые передаются как элементы.

Наши структуры `InputCommand`, `DeviceCommand`, `IrJob` и `DiagnosticEvent` не зависят от FreeRTOS. Дескрипторы `QueueHandle_t` и операции `xQueueSend()` / `xQueueReceive()` относятся к выбранному механизму обмена между задачами.

Для создания очереди нужны два параметра:

- ёмкость — сколько элементов очередь может хранить одновременно;
- размер одного элемента в байтах — например, `sizeof(InputCommand)`.

Ёмкости хранятся в `App_Config::Queues`. Начальные значения: по 8 элементов для `q_input`, `q_audio`, `q_tv`, `q_ir_tx` и 32 элемента для `q_diag`.

| Очередь | Тип элемента |
|---|---|
| `q_input` | `InputCommand` |
| `q_audio` | `DeviceCommand` |
| `q_tv` | `DeviceCommand` |
| `q_ir_tx` | `IrJob` |
| `q_diag` | `DiagnosticEvent` |

Типы и ёмкости сами по себе ещё не создают очереди. Для внутренних структур используем `sizeof`, учитывающий возможное выравнивание; их размещение в памяти не обязано совпадать с форматом UART-кадра.

### 11.2. Дескриптор `QueueHandle_t`

`QueueHandle_t` — тип дескриптора очереди FreeRTOS. В используемой реализации это указатель на внутреннюю структуру очереди. Приложение передаёт его функциям FreeRTOS и не обращается к полям этой внутренней структуры напрямую.

```cpp
QueueHandle_t q_input = nullptr;
```

`nullptr` — нулевой указатель C++. В нашем контексте он обозначает, что очередь ещё не создана. Эта строка создаёт только переменную для дескриптора, а не саму очередь и её буфер.

Это обычное объявление переменной: `QueueHandle_t` — её тип, `q_input` — имя, `nullptr` — начальное значение. В FreeRTOS имя типа объявлено через `typedef`:

```cpp
typedef struct QueueDefinition* QueueHandle_t;
```

Поэтому `QueueHandle_t q_input = nullptr;` по смыслу равнозначно объявлению указателя `struct QueueDefinition* q_input = nullptr;`. Слово «дескриптор» описывает назначение указателя, а не особую конструкцию языка или таблицу «имя — значение».

Сначала указатель ни на какой объект не указывает. После успешного `xQueueCreate()` в него сохраняется указатель на созданную очередь. При неудаче создания возвращается нулевой указатель; результат нужно проверить до использования очереди.

После создания дескриптор указывает, с какой очередью должны работать `xQueueSend()` и `xQueueReceive()`. Подробности этих операций добавим после разбора их применения.

### 11.3. Контекст очередей приложения

Предложенный интерфейс `App_Context::Queues` объединяет пять дескрипторов. `CreateQueues(Queues& queues)` должна заполнить их при запуске приложения, до старта рабочих задач.

- На входе дескрипторы равны `nullptr`.
- `true` означает, что созданы все пять очередей.
- При частичной ошибке создания функция должна освободить уже созданные очереди и вернуть `false`; задачи в этом случае не запускаются.

Это контракт нашей функции, а не автоматическое поведение структуры C++. Объявление функции в заголовке ещё не реализует создание и освобождение ресурсов.

При вызове `CreateQueues()` фактически заполняем поля структуры `Queues` указателями на созданные очереди вместо начальных `nullptr`:

```cpp
queues.q_input = xQueueCreate(
    App_Config::Queues::INPUT_LENGTH, sizeof(InputCommand));
```

Переменная-указатель `queues.q_input` уже существует как поле структуры. Справа `xQueueCreate()` создаёт саму очередь с заданными ёмкостью и размером элемента, а возвращённый указатель сохраняется в это поле. Сама очередь не размещается внутри структуры `Queues`: структура хранит только дескрипторы. При неудаче создания поле получает нулевой указатель.

Дескриптор указывает на служебный объект очереди, а не непосредственно на буфер элементов. В служебном объекте FreeRTOS хранит сведения о ёмкости, размере элемента, текущем заполнении и расположении буфера.

FreeRTOS не знает состав полей `InputCommand`: при создании ей достаточно количества элементов и размера одного элемента. Буфер данных требует `INPUT_LENGTH * sizeof(InputCommand)` байт; дополнительно нужна память для служебного объекта. `sizeof(InputCommand)` — размер структуры в байтах, а `std::size_t` — тип результата оператора `sizeof`.
